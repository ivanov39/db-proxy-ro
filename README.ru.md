# db-proxy-ro

Прокси только для чтения к **PostgreSQL** и **MySQL / MariaDB**.

Клиент подключается к прокси так, будто это сама база: без пароля или с любым
именем и паролем, и указывает только имя базы данных. Прокси находит базу в
файлах параметров, подключается к настоящему серверу с настоящими учётными
данными и передаёт трафик. Чтение проходит, любое изменение данных отклоняется.

Типичное применение: дать людям, скриптам или ИИ-агентам доступ к боевой базе,
не раздавая пароли и не рискуя случайной записью.

English version: [README.md](README.md)

```
psql / mysql / приложение ──► db-proxy-ro ──► настоящая база
      (без пароля)             │  отклоняет запись    (учётные данные
                               │  пишет лог запросов   из params/*.toml)
```

## Быстрый старт

```sh
git clone https://github.com/ivanov39/db-proxy-ro.git && cd db-proxy-ro

mkdir -p params/pgsql params/mysql
cp examples/params/pgsql/example.toml params/pgsql/app.toml   # и отредактировать
cp examples/params/mysql/example.toml params/mysql/shop.toml  # и отредактировать

docker compose up -d --build
```

Подключение: только имя базы.

```sh
psql  -h 127.0.0.1 -p 25432 app_db
mysql -h 127.0.0.1 -P 23306 --protocol=tcp app_db
```

```
app_db=> delete from users;
ERROR:  db-proxy-ro: DELETE statements are not allowed: the proxy is read-only
```

## Список баз данных

Каждый клиент получает список баз своим родным способом и видит базы,
настроенные в прокси для этой СУБД, а не базы сервера за ним.

**PostgreSQL** — `\l` в `psql`, дерево баз в графических клиентах или любой
запрос к `pg_database`:

```
app_db=> \l
app_db=> select datname from pg_database;
```

Прокси переписывает обращения к таблице каталога `pg_database` так, что в ней
оказывается по одной строке на каждую базу прокси; `current_database()`
возвращает имя, с которым вы подключились. Остальные колонки (владелец,
кодировка, правила сортировки, …) берутся от базы, к которой подключена
сессия. Чтобы переключиться, подключитесь заново — `\c other_db` в `psql`.
Нужен PostgreSQL 12 или новее на стороне базы.

Подключение PostgreSQL всегда идёт к какой-то базе. Клиент, не указавший базу
(тогда он присылает имя пользователя или `postgres`), подключается к базе по
умолчанию: `DBPROXY_PGSQL_DEFAULT_DB` или первой по имени. Оттуда он может
получить список остальных. Любое другое неизвестное имя — ошибка, в которой
перечислены доступные базы.

**MySQL** — `SHOW DATABASES` (в том числе с `LIKE 'шаблон'`):

```sh
mysql -h 127.0.0.1 -P 23306 --protocol=tcp
mysql> show databases;
mysql> use app_db;
```

Клиент, не указавший базу, подключается к базе по умолчанию:
`DBPROXY_MYSQL_DEFAULT_DB` или первой по имени. `USE` с именем из списка
переключает сессию на эту базу, даже если она на другом сервере; любое другое
имя — это схема текущего сервера.
`SHOW DATABASES` нужно отправлять обычным запросом, а не подготовленным
выражением.

### Все базы MySQL в одной сессии

Графические клиенты строят дерево схем по `information_schema` через одно
соединение. Чтобы в дереве были все базы прокси, а не только та, к которой
подключена сессия, прокси (при включённом `DBPROXY_MYSQL_ALL_DATABASES`, это
значение по умолчанию):

* выполняет `SELECT` к `information_schema` на **каждой** базе MySQL из прокси
  и возвращает строки всех баз без дубликатов. Если в запросе названа схема
  (`where table_schema = 'app_db'`), опрашивается только эта база;
* выполняет `SELECT`, в котором названа другая база (`select … from other_db.t`),
  на этой базе.

Дополнительные соединения с базами открываются при первом обращении, по одному
на базу, работают в режиме «только чтение», как и основное, и закрываются,
когда клиент отключается. Учитывайте лимиты соединений на серверах: одна
клиентская сессия может держать соединение с каждой настроенной базой.

Ограничения: объединённые строки заново не сортируются, поэтому `ORDER BY`,
`LIMIT` и агрегаты действуют в пределах одной базы; запрос, соединяющий таблицы
двух баз прокси, не поддерживается; маршрутизация идёт по настоящему имени
схемы и только для обычных (не подготовленных) запросов.

## Параметры баз данных

Один TOML-файл на одну базу, в `params/pgsql/` или `params/mysql/`:

```toml
host     = "pg.example.internal"
port     = 5432
user     = "app_user"
password = "secret"
name     = "app_db"            # имя базы на сервере

# alias   = "app_db_prod"      # необязательно: имя для клиентов (по умолчанию name)
# sslmode = "prefer"           # необязательно: disable | prefer | require | verify-full
```

* Файлы читаются **один раз, при старте**. После изменения перезапустите
  контейнер: `docker compose restart`.
* Прокси не запустится, если файл некорректен или если два файла одной СУБД
  задают одно и то же имя базы для клиентов. Причина будет в `logs/error.log`.
* При старте прокси к базам не подключается. Соединение с базой открывается,
  когда подключается клиент: одно соединение с базой на одно клиентское.
* Имена хостов разрешаются изнутри контейнера. С прилагаемым
  `docker-compose.yml` (сеть хоста) это то же самое, что на хосте, включая
  маршруты VPN и внутренний DNS.

Каталог `params/` внесён в `.gitignore`; не коммитьте учётные данные.

## Настройки

Переменные окружения; для Docker Compose их кладут в `.env`
(см. [.env.example](.env.example)).

| Переменная | По умолчанию (compose) | Назначение |
|---|---|---|
| `DBPROXY_PGSQL_LISTEN` | `127.0.0.1:25432` | Адрес для клиентов PostgreSQL |
| `DBPROXY_MYSQL_LISTEN` | `127.0.0.1:23306` | Адрес для клиентов MySQL |
| `DBPROXY_PGSQL_DEFAULT_DB` | первая по имени | База для клиентов PostgreSQL, не указавших базу |
| `DBPROXY_MYSQL_DEFAULT_DB` | первая по имени | База для клиентов MySQL, не указавших базу |
| `DBPROXY_MYSQL_ALL_DATABASES` | `true` | Одна сессия MySQL видит все базы прокси (см. «Список баз данных») |
| `DBPROXY_LOG_LEVEL` | `info` | Уровень служебного лога: `debug`, `info`, `warn`, `error` |
| `DBPROXY_CONNECT_TIMEOUT` | `10s` | Лимит времени на подключение к базе |
| `DBPROXY_MYSQL_SERVER_VERSION` | `8.0.36-db-proxy-ro` | Версия, которую видят клиенты MySQL в приветствии |
| `DBPROXY_LOG_SQL_MAX_LEN` | `8192` | Более длинный SQL в логе запросов обрезается; `0` — без ограничения |
| `DBPROXY_SHUTDOWN_TIMEOUT` | `5s` | Сколько ждать открытые сессии при остановке |
| `DBPROXY_PARAMS_DIR` | `/params` | Каталог с файлами параметров |
| `DBPROXY_LOG_DIR` | `/logs` | Куда контейнер перенаправляет логи; пусто — в `docker logs` |
| `DBPROXY_UID`, `DBPROXY_GID` | `1000` | Пользователь, от которого работает контейнер (только compose) |

> **Прокси не проверяет клиентов.** Любой, кому доступны его порты, может
> читать настроенные базы. Держите его на `127.0.0.1` или в доверенной сети.

## Логи

Процесс пишет лог запросов в stdout, а служебный лог — в stderr, оба в формате
JSON lines. Entrypoint контейнера перенаправляет их в файлы в смонтированном
каталоге `./logs`:

* `logs/query.log` — каждый запрос: база, клиент, SQL, длительность, число
  строк и ошибка базы, если была; у отклонённых запросов `"msg":"rejected"` и
  поле `reason`.
* `logs/error.log` — запуск, остановка, неудачные подключения к базам,
  оборванные сессии.

Файлы открываются в режиме дозаписи, поэтому `logrotate` с `copytruncate`
работает. SQL пишется в лог как есть, вместе с литералами.

## Как обеспечивается режим «только чтение»

Два независимых слоя; запись должна пройти оба.

1. **SQL-фильтр в прокси.** Каждый текст SQL (обычные запросы и подготовленные
   выражения) разбирается на лексемы и сверяется с белым списком: `SELECT`,
   `WITH`, `SHOW`, `EXPLAIN`, управление транзакциями, сессионный `SET` и ещё
   несколько. Внутри разрешённой команды тоже отклоняется всё, что меняет
   данные: модифицирующие CTE, `SELECT … INTO`, `FOR UPDATE`, `COPY … FROM`,
   `EXPLAIN ANALYZE` для записи, функции вроде `nextval()` и `set_config()`.
   Всё, чего фильтр не понимает, отклоняется.
2. **Сессия только для чтения на стороне базы.** Каждая сессия открывается в
   режиме read-only транзакций (`default_transaction_read_only=on` для
   PostgreSQL, `SET SESSION TRANSACTION READ ONLY` для MySQL), поэтому сама
   база отклоняет запись, которую фильтр увидеть не может, например внутри
   хранимой функции. Фильтр отклоняет любые команды, способные выключить этот
   режим, а на PostgreSQL 14+ прокси ещё и разрывает сессию, если сервер
   сообщает, что режим изменился.

Там, где SQL неоднозначен, фильтр намеренно строг: запрос принимается, только
если он безвреден при любых настройках сервера, влияющих на разбор
(`standard_conforming_strings`, `NO_BACKSLASH_ESCAPES`, `ANSI_QUOTES`).

### Чего прокси гарантировать не может и как это закрыть

Режим «только чтение» — свойство сессии, а не соединения: он включается при
открытии сессии и теоретически может быть выключен командой, выполненной
внутри неё. Прокси отклоняет все известные ему такие команды, но сделать
выключение невозможным не может. Это может только сама база:

1. **Учётная запись только с правами `SELECT`.** Что бы ни дошло до базы,
   записать под ней нельзя. Это самый надёжный вариант.
2. **Подключение прокси к реплике только для чтения** вместо мастера, если
   она есть. Реплика не принимает запись вообще.

Оба варианта задаются только в файлах параметров (`user`, `password`, `host`);
в прокси ничего менять не нужно. В этом случае прокси — второй рубеж защиты, а
не единственный.

## Ограничения

* **Нет TLS и аутентификации со стороны клиента.** Клиент должен подключаться
  с выключенным или необязательным TLS (`sslmode=prefer`,
  `--ssl-mode=PREFERRED` — это значения по умолчанию). Соединение прокси с
  базой может использовать TLS (`sslmode`).
* **Строгость даёт ложные отказы.** Примеры: колонка с именем `update` или
  `delete` без кавычек (возьмите в кавычки), `SELECT … INTO @var`, исполняемые
  комментарии MySQL `/*! … */`, `CALL`, SQL-команды `PREPARE`/`EXECUTE` в MySQL,
  `DO`. Инструменты, которым это нужно (например, `mysqldump`, блокирующий
  таблицы), через прокси не работают; `pg_dump` тоже не поддерживается.
* **PostgreSQL**: нужно прямое соединение с сервером или пулер в сессионном
  режиме. Пулер в транзакционном режиме не сохранит режим read-only, а прокси
  отказывается работать, если не может подтвердить этот режим. Репликационные
  подключения и протокол вызова функций отклоняются. Из стартовых параметров
  клиента передаётся только безопасное подмножество (`application_name`,
  `client_encoding`, `search_path`, …); `options` отбрасывается.
* **PostgreSQL старше 14** не сообщает об изменении режима read-only, поэтому
  автоматический разрыв сессии там недоступен. Это важно, только если в базе
  уже есть функция, которая выключает этот режим.
* **MySQL / MariaDB**: проверено на MySQL 5.7 и 8.0 и MariaDB 11, с учётными
  записями `mysql_native_password` и `caching_sha2_password`
  (`sha256_password` реализован, но тестами не покрыт; другие плагины,
  например `ed25519` в MariaDB, не поддерживаются). `COM_CHANGE_USER`, команды
  репликации и `LOAD DATA LOCAL` отклоняются. Сжатие протокола не предлагается.
  Временные таблицы в read-only транзакции MySQL остаются доступными для
  записи, но до сервера доходят только команды из белого списка.
* Файлы параметров перечитываются только при перезапуске.

## Архитектура

Go, Clean Architecture; зависимости направлены внутрь.

```
cmd/db-proxy-ro            точка входа
internal/
  domain/                  сущности и правила, без зависимостей
    sqlguard/              политика «только чтение»: лексер и белый список
  usecase/                 логика приложения и порты (TargetSource, AuditLog)
  infrastructure/          адаптеры: настройки из окружения, TOML-файлы, логи
  transport/               адаптеры: сетевые протоколы
    netserver/             приём TCP-соединений, корректная остановка
    pgsql/                 ретрансляция протокола PostgreSQL
    mysql/                 ретрансляция протокола MySQL
  app/                     сборка зависимостей
```

После рукопожатия оба протокола передаются как есть, сообщение за сообщением;
разбираются только сообщения клиента, несущие SQL. Результаты запросов
передаются потоком и целиком в памяти не накапливаются.
